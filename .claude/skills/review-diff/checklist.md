# review-diff チェックリスト(このリポジトリで蓄積したレビュー知見)

`/review-diff` の実行時に必ず読み、該当する差分があれば各項目を確認する。
項目ごとに **既定の重大度** を示す。状況により上下させてよいが、その場合は理由を指摘に書く。

## 追加・更新のルール

- レビューで「今後も毎回確認すべき」と判断した指摘は、このファイルに1項目として追記する。
- 誤検知や、合意済みで指摘不要になったパターンは「指摘しないもの」に追記する。
- 各項目には、きっかけになった課題やコミットを `(由来: ...)` で残す。
- 項目が増えすぎたら統合・削除して整理する(レビュー時間と指摘の多さに直結するため)。

## 重大度の基準

- **🔴 must:** 誤った結果を返す、例外で落ちる、サーバー側の不具合がクライアントの誤り(400)として隠れる、秘密情報の混入。
- **🟡 should:** 設計書(`specs/<slug>/README.md`)と実装の不一致、防御のつもりで実際には効いていないコード、
  条件によっては何も検証しないテスト。
- **🔵 nits:** 保守性・可読性の改善、合意済みの慣行に沿った重複。

## 例外処理と HTTP ステータス

- [ ] **🔴 must:** `GlobalExceptionHandler` に `IllegalArgumentException` など汎用例外の全域ハンドラを追加していないか。
      他の処理のサーバー側不具合まで 400 に見せかけ、内部メッセージを露出させる。
      algo 層の制約違反は、エンドポイント内で `ResponseStatusException(BAD_REQUEST)` に変換する。
      (由来: run-length-window-sum)
- [ ] **🟡 should:** コントローラーで `IllegalArgumentException` を 400 に変換する `try` の範囲が、
      入力検証に由来する例外だけに限定されているか。シミュレーター実行や後続処理まで囲むと、
      アルゴリズムの不具合が 400 として隠れる。(由来: treasure-excavation)
- [ ] **🟡 should:** フィールドや要素をまたぐ制約(`l ≤ r`、重複、偶数個など)が Bean Validation で表せない場合、
      algo 層で検出してコントローラーで 400 に変換しているか。変換漏れは 500 になる。

## 設計書との整合

- [ ] **🟡 should:** `algo/<pkg>/` の変更が `specs/<slug>/README.md` の本文(2章の入出力・例外、5章の処理の流れ)と一致しているか。
      シーケンス図だけ更新して本文が古いまま、という不一致に注意する。(由来: nth-spell 5.2)
- [ ] **🟡 should:** 設計書で「検証しない」「結果は未定義」とした入力について、実装が例外で落ちない(配列の範囲外アクセスなど)か。
      (由来: odd-even-tree)
- [ ] **🔵 nits:** 設計書の計算量の表記が実装と合っているか(例: Union-Find で union by size を使わないなら `α(N)` ではない)。
      (由来: odd-even-tree)

## テスト

- [ ] **🟡 should:** 条件分岐の中だけで assert するテスト(`if (...) { assertThat(...) }`)は、
      その条件が実際に1回以上成立しているか。成立しないと何も検証せずに通る。
      少なくとも1回成立したことを最後に assert する。(由来: number-baseball の "4S 0B" テスト)
- [ ] **🟡 should:** ランダム比較テストの総当たり(オラクル)が、実装と同じ変換・同じ性質に依存していないか。
      同じ前提を使うと実装のバグを検出できない。(由来: nth-spell / odd-even-tree で独立な総当たりを採用)
- [ ] **🔵 nits:** `assertTimeout` を使う性能テストで JIT のウォームアップをしているか。CI で不安定にならない余裕があるか。

## 入力検証

- [ ] **🟡 should:** 例外の種類が同じクラス内で一貫しているか(例: 他の入力は `IllegalArgumentException` なのに、
      `null` だけ `NullPointerException` になる)。(由来: treasure-excavation の FixedTreasureExcavator)
- [ ] **🔵 nits:** 正規表現での形式検証は全体一致(`matches()` / `@Pattern`)になっているか。部分一致だと不正な文字列が通る。

## スクリプト・フック(`.githooks/` など)

- [ ] **🔴 must:** Git for Windows の bash で `/` から始まる引数(例: `claude -p "/review-diff"`)を渡す場合、
      `MSYS_NO_PATHCONV=1` を付けているか。付けないと Windows パスに書き換えられる。(由来: pre-commit フック)
- [ ] **🟡 should:** フックファイルが実行ビット付き(`100755`)でステージされているか。Linux/macOS では実行ビットが無いと無視される。
- [ ] **🟡 should:** 権限ルールによる防御(`--disallowedTools` など)が、プレフィックス一致の都合で実際に効いているか。
      効かない防御はコメントで正直に書く。(由来: pre-commit フックの `git diff --output`)

## 指摘しないもの(合意済みの慣行)

- 上限値や正規表現が Bean Validation のアノテーションと algo 層の定数に重複して書かれていること(既存課題すべての慣行)。
  指摘するとしても 🔵 nits にとどめる。
- コントローラーのメソッドシグネチャが 100 桁を少し超えること(既存エンドポイントと同じ形)。
