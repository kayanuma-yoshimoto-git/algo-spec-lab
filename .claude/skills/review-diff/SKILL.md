# /review-diff 指示書

現在の作業ツリーの git 差分を収集し、変更内容に対してコードレビューを行ってください。
コードの変更は行わず、**レビュー結果の報告のみ**を出力します。

## 実行手順
1. 差分を収集します。
   - `git status --short` で変更ファイル一覧を把握
   - `git diff HEAD` で未コミットの変更（staged + unstaged）を取得
   - 新規追加ファイルは `git status` で検出し、内容を読む
   - 差分が空の場合は「レビュー対象の変更なし」と報告して終了
2. 変更の意図を把握します。差分が `algo/<pkg>/` 配下を含む場合は対応する `specs/<slug>/README.md` を、それ以外は必要に応じて既存コードや `CLAUDE.md` の規約を参照します。
3. 下記の観点でレビューし、報告フォーマットに従って出力します。

## レビュー観点
- **正しさ (Correctness):** ロジックの誤り、境界値・null・空・例外パスの考慮漏れ、`README.md` の仕様・テストケースとの不一致
- **設計 (Design):** 責務分離（コントローラーにロジックを溜めていないか）、SOLID、命名、重複
- **規約準拠:** `CLAUDE.md` の規約（Google Java Style、日本語ドキュメント/コメント、秘密情報の非混入）
- **テスト:** 変更に対応するテストの有無、正常系・異常系の網羅
- **セキュリティ:** 認証情報・秘密鍵・本番接続情報の混入、入力バリデーションの欠如

## 報告フォーマット

~~~markdown
# コードレビュー結果

## 対象
- ブランチ: <現在のブランチ>
- 変更ファイル: <件数> 件

## 指摘事項
### 🔴 must（修正が必要）
- `path/to/File.java:123` — 指摘内容 / 理由 / 修正案

### 🟡 should（修正が望ましい）
- `path/to/File.java:45` — 指摘内容 / 理由 / 修正案

### 🔵 nits（任意）
- `path/to/File.java:9` — 指摘内容

## 良かった点
- <あれば記載>

## 総評
- <マージ可否の判断と根拠>
~~~

## 規約
- 指摘には必ず `ファイルパス:行番号` を添える。
- 各指摘は「何が問題か」「なぜ問題か」「どう直すか」をセットで書く。
- 指摘が無い観点は「問題なし」と明記し、省略しない。
- 憶測でコードを断罪しない。確認が必要な箇所は「要確認」として質問形式で挙げる。
