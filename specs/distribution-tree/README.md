# 分配ツリーのリーフ数最大化

- **slug:** distribution-tree
- **実装パッケージ:** com.example.algospeclab.algo.distributiontree
- **公開API:** `POST /api/algorithms/distribution-tree`(既存 `AlgorithmController` に追加)

## 1. 問題の概要

ルートノード・リーフノード・分配ノードからなるツリーを1つ構成し、**リーフノードをできるだけ多く** 作る。

- ルートノードは子を **ちょうど1つ** 持つ。ルート以外のノードは子を **2つ・3つ・0個** のいずれかで持つ。
- 子が0個のノードがリーフノード、ルートでもリーフでもないノード(子が2つか3つ)が **分配ノード**。
- 分配ノードは最大 `dist_limit` 個まで置ける。
- **同じ深さにある分配ノードは、すべて同じ数の子を持つ**(深さ = ルートからの最短経路長)。
- 各リーフノードの **分配度** は、そのリーフの親からルートまでの経路上にある全ノードの子の数の積
  (例: 経路上の子の数が `2, 3, 3, 1` なら `2 × 3 × 3 × 1 = 18`)。
- すべてのリーフの分配度は `split_limit` 以下でなければならない。

`dist_limit` と `split_limit` が与えられたとき、作れるリーフノード数の最大値を返す。

## 2. 入出力の定義

### 2.1 アルゴリズム関数(algo 層)

- **クラス / メソッド:** `DistributionTree.solve(int distLimit, int splitLimit)`
- **入力:**
  - `distLimit: int` — 置ける分配ノード数の上限(`0 ≤ distLimit ≤ 10^9`)
  - `splitLimit: int` — 分配度の上限(`1 ≤ splitLimit ≤ 10^9`)
- **出力:** `int` — リーフノード数の最大値
  - 5.1 の性質から答えは `splitLimit` 以下(`≤ 10^9`)なので `int` に収まる。途中計算は `long` で行う。
- **不正入力:** 範囲外の値は `IllegalArgumentException` を送出する。

### 2.2 REST API(controller 層)

- `POST /api/algorithms/distribution-tree`
- リクエスト DTO: `DistributionTreeRequest(int distLimit, int splitLimit)`
  ```json
  { "distLimit": 3, "splitLimit": 6 }
  ```
- レスポンス DTO: `DistributionTreeResponse(int leaves)`
  ```json
  { "leaves": 6 }
  ```
- コントローラーは algo 層に委譲するだけでロジックは持たない。
- 値域(`0 ≤ distLimit ≤ 10^9`、`1 ≤ splitLimit ≤ 10^9`)は Bean Validation で検証し、
  違反時は既存の `GlobalExceptionHandler` により `400` を返す(フィールドをまたぐ制約は無い)。

## 3. 制約条件

- `0 ≤ distLimit ≤ 10^9`、`1 ≤ splitLimit ≤ 10^9`
- 分配ノードを持つ深さの数は、子の数の積が `splitLimit` 以下になる必要があるため最大 `log2(10^9) ≈ 30`。
- **時間計算量:** 深さの構成(2 の個数 `a` と 3 の個数 `b`)が最大約 `30 × 19` 通り、
  それぞれで「満杯でない深さ」を最大30通り試すため、全体で数万回程度の演算(実測 0.1ms 程度)。
- **空間計算量:** `O(log splitLimit)`
- 分配ノード数・リーフ数の途中計算は `10^9` を超えうるため `long` で行う。

## 4. 正常系と異常系の定義 (Test Cases)

### 正常系 (Normal Cases)

- [ ] 問題例1: `distLimit=3, splitLimit=6` → `6`
- [ ] 問題例2: `distLimit=0, splitLimit=10` → `1`(分配ノードを置けず、ルートの子1つだけがリーフ)
- [ ] 問題例3: `distLimit=3, splitLimit=100` → `7`
- [ ] 問題例4: `distLimit=5, splitLimit=16` → `9`(分配ノードは5個まで置けるが、4個で最大になる)
- [ ] 「3 の深さを先に置く」貪欲法では解けない例: `distLimit=3, splitLimit=6` → `6`
      (子の数を 3 → 2 の順にすると5個。2 → 3 の順で6個)
- [ ] 「上の深さから満杯に埋める」貪欲法では解けない例: `distLimit=12, splitLimit=24` → `19`
      (子の数 `2, 2, 2, 3` の深さで分配ノードを `1, 2, 3, 6` 個と置く。3段目を満杯(4個)にすると18個)
- [ ] **総当たりとの一致:** `0 ≤ distLimit ≤ 40`、`1 ≤ splitLimit ≤ 300` の全組み合わせで、
      テスト内で独立に実装した総当たり(メモ化再帰)と結果が一致する

### 異常系・限界値 (Edge Cases)

- [ ] `splitLimit=1` → どの `distLimit` でも `1`(子を2つ以上持つ分配ノードを置けない)
- [ ] `distLimit=1, splitLimit=2` → `2`、`distLimit=1, splitLimit=3` → `3`
- [ ] 最大値: `distLimit=10^9, splitLimit=10^9` → `967458816`(設計時の計算値。回帰テストとして固定)
- [ ] `distLimit` が小さく `splitLimit` が十分大きい: `distLimit=10, splitLimit=10^9` → `21`
      (すべて子3つの分配ノードにでき、`1 + 2 × 10`)
- [ ] `distLimit=10^9, splitLimit=1` → `1`、`distLimit=0, splitLimit=10^9` → `1`
- [ ] 最大値の入力でも十分短時間(目安 100ms 以内)で完了する
- [ ] `distLimit` が負、または `10^9` 超過 → `IllegalArgumentException`
- [ ] `splitLimit` が `0` 以下、または `10^9` 超過 → `IllegalArgumentException`

### 異常系 — REST API 層

- [ ] 正常な入力(`distLimit=3, splitLimit=6`) → `200` かつ `{ "leaves": 6 }`
- [ ] `distLimit` が範囲外(`-1`、`1000000001`) → `400`
- [ ] `splitLimit` が範囲外(`0`、`1000000001`) → `400`

## 5. 設計のアプローチ

**採用方式: 深さごとの子の数の並びを列挙し、各並びで「1段だけ満杯でない」配置を解析的に評価する**

### 5.1 問題の言い換え

- 深さ `i`(ルートの子を深さ1とする)で分配ノードを `m_i` 個置き、その子の数を `c_i ∈ {2, 3}` とする。
  深さ `i+1` のノード数は `m_i × c_i` なので、`m_{i+1} ≤ c_i × m_i`(`m_1 ≤ 1`)。
- 分配ノード1個は、リーフ1個を `c` 個の子に置き換えるので、リーフは `c - 1` 個増える。
  よって **リーフ数 = `1 + Σ m_i × (c_i - 1)`**、分配ノード数 = `Σ m_i ≤ distLimit`。
- 分配度は同じ深さのリーフで等しく、深いほど大きい。したがって分配度の制約は
  **分配ノードを持つ全深さの子の数の積 `c_1 × c_2 × … × c_k ≤ splitLimit`** と同値になる。
- 各リーフの「重み」`1 / 分配度` の総和は常に1なので、リーフ数は `splitLimit` 以下(答えが `int` に収まる根拠)。

### 5.2 なぜ単純な貪欲法ではだめか

- **3 を先に置く:** `distLimit=3, splitLimit=6` では、子の数 `3 → 2` だと 1 + 2 + 2 = 5 個、
  `2 → 3` だと 1 + 1 + 4 = 6 個。子3つの分配ノード(1個あたり +2)を、容量の大きい深い段に多く置くほうが得になる。
- **上の深さから満杯に埋める:** `distLimit=12, splitLimit=24`、子の数 `2, 2, 2, 3` では、
  満杯に埋めると `m = (1, 2, 4, 5)` で18個。3段目を1個減らして `m = (1, 2, 3, 6)` とすると
  子3つの段に1個多く置けて19個になる。+1 しか増やさない段をあえて満杯にしないほうが得な場合がある。

### 5.3 採用する解法

`m_i` についての線形計画(`m_{i+1} ≤ c_i m_i`、`Σ m_i ≤ distLimit`)の最適解は頂点にあり、
頂点では「満杯でない(`m_{i+1} < c_i m_i`)段が高々1つ」になる。これを踏まえ、次のように全候補を評価する。

1. 子の数の並びとして、**2 を `a` 個 → 3 を `b` 個** の順(`2^a × 3^b ≤ splitLimit`)をすべて列挙する。
   2 を上に置くほうが上の段の分配ノード数(支えのコスト)が小さく、子3つの段を深く・多くできる。
2. 各並び(段数 `k = a + b`)について、満杯でない段 `j`(0始まり、`0 ≤ j < k`)を試す。
   - 段 `0 .. j-1` は満杯: 分配ノード数の合計 `A = Σ_{i<j} P_i`(`P_i` = 段 `i` の容量 = `c_0 … c_{i-1}`)。
   - 段 `j` に `y` 個置き(`1 ≤ y ≤ P_j`)、段 `j+1 .. k-2` は `y` を起点に満杯にする。
     その分配ノード数は `y × B`(`B = Σ_{i=j}^{k-2} Q_i`、`Q_j = 1`、`Q_{i+1} = Q_i × c_i`)。
   - 最後の段 `k-1` には、残り予算と容量の小さいほう `r = min(y × C, distLimit - A - y × B)` 個を置く(`C = Q_{k-1}`)。
   - リーフ数 = `P_j + y × (C - 1) + r × (c_{k-1} - 1)`(満杯の段の増分は積の差に畳み込める)。
   - これは `y` について折れ線なので、`y ∈ {1, yMax, y*, y*+1}`(`y* = ⌊(distLimit - A) / (B + C)⌋` は折れ目、
     `yMax = min(P_j, ⌊(distLimit - A) / B⌋)`)だけを評価すればよい。`j = k-1` のときは `r = min(P_j, distLimit - A)`。
3. 分配ノードを置かない場合の `1` を含め、全候補の最大値を返す。

### 5.4 検証結果と注意点

- 「2 → 3 の順だけを見ればよい」ことと「整数への丸めは `y*`・`y*+1` で十分」ことは厳密には証明していない。
  代わりに、設計時のプロトタイプで総当たり(メモ化再帰で全配置を探索)と照合し、次の範囲で **完全に一致** することを確認済み。
  - `0 ≤ distLimit ≤ 40`、`1 ≤ splitLimit ≤ 300` の全 12,300 通り
  - `distLimit ≤ 150`、`splitLimit ≤ 5,000` のランダム 2,000 通り
  - 問題例1〜4
- 同じ総当たりをテストにも組み込み、回帰を防ぐ(4章の「総当たりとの一致」)。
- 最大入力 `(10^9, 10^9)` の値 `967458816` は総当たりでは確認できない範囲のため、本解法の計算値を回帰テスト用に固定する。
